# PRD-008 pull request description

## Title

Add versioned pipeline runs and selective replay

## Summary

This PR adds immutable pipeline definitions, component invocations, strict output validation,
selective replay, explicit result publication, PostgreSQL persistence, inspection APIs, and a
pipeline-history workbench tab. It implements PRD-008 only; workload execution remains deferred to
PRD-013 and PRD-014.

## Architecture changes

- Adds strict canonical contracts for pipeline DAGs, runs, component evidence/results,
  publications, and complete run history, with committed JSON Schemas.
- Registers every component output schema against canonical Pydantic contracts before accepting a
  pipeline definition.
- Materializes stable parent invocation UUIDs for each run and preserves raw and normalized output,
  producer/configuration/version identity, evidence, warnings, trace, latency, and cost.
- Converts schema-invalid reported successes into immutable failed results without losing raw or
  attempted normalized output.
- Creates selective replays as new invocations with explicit origin and trace identifiers.
- Requires published values and artifacts to match their successful producing invocations.
- Adds PostgreSQL tables and constraints for definitions, runs, attempts, DAG/replay edges, artifact
  associations, and publications.
- Adds explicit HTTP-only adapters and a read-only **Runs** tab in the source workbench.

## Migration table

| Previous behavior | PRD-008 behavior | Reason |
|---|---|---|
| Extraction summaries and cache files identified a run implicitly | Versioned pipeline definition and run records have stable UUIDs | Runs must be comparable and reproducible. |
| Component output could be interpreted only from local files | Raw, normalized, evidence, configuration, producer, warning, trace, cost, and latency fields share one invocation record | Every model/tool result needs inspectable provenance. |
| Rerunning meant replacing or regenerating workflow files | Replay appends a new invocation linked to the prior attempt | Historic results cannot be destructively replaced. |
| Invalid normalized output failed before durable registration | Validation failure is a terminal, queryable result retaining both attempted representations | Failures are evaluation data. |
| Final values lacked exact producer links | Publication validates each value against a producer invocation and JSON Pointer | Scientific values must identify their computation. |

Migration `0007_pipeline_run_registry` is additive. Its manual down migration removes only the new
registry tables in reverse dependency order; running it destroys pipeline provenance and is not
automatic.

## Preserved behavior

- Evaluation cases, predictions, reviewer annotations, revisions, and adjudications remain separate
  and unchanged during runs and replays.
- Artifact bytes remain immutable in S3/MinIO; registry rows store strict references rather than
  binary payloads.
- Existing extraction continues through the retained hackathon entry point until PRD-011.
- Workbench source loading and overlays continue even if pipeline history cannot be loaded.
- Canonical contracts reject unknown fields and coercible-only internal values.

## Manual verification

1. Register a two-component definition with known output schemas and create a run for an evaluation
   case whose input is one of its immutable source artifacts.
2. Complete the parent with valid normalized JSON and verify a second terminal submission returns
   `409`.
3. Report malformed normalized JSON for the child and verify the invocation is `failed` with
   `output_validation`, raw output, attempted normalized output, and a validation issue.
4. Replay only that invocation, verify its UUID and trace differ, and confirm the failed attempt is
   still queryable.
5. Complete the replay with valid output and publish a value pointing to its exact JSON Pointer.
6. Alter the published value and verify publication fails without changing history.
7. Open `/workbench/<case-id>`, select **Runs**, and inspect producer versions, attempt states,
   replay origin, raw/normalized output, trace, cost, latency, warnings, and publication count.

## Known limitations and deferred work

- The registry records work but does not execute it. Leases, heartbeats, cancellation, logs,
  retries, and local Docker execution begin in PRD-013.
- Component replay is an explicit API operation; Temporal workflow orchestration is not yet added.
- The workbench history tab is inspect-only and does not submit replays.
- Output schemas must be canonical v1 contracts registered in-process; external schema catalogs and
  schema migrations are deferred.
- Authentication, organization visibility enforcement, and private traces arrive in PRD-017.
- Existing western-blot extraction is migrated into these contracts in PRD-011.
