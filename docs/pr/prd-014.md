# PRD-014 pull request description

## Title

Deploy HiveBlot services and workers to Kubernetes

## Summary

This PR makes Kubernetes the deployed placement runtime while preserving PostgreSQL and immutable
object storage as the durable generic-job state boundary. It adds a production-oriented Kustomize
base, local kind automation, a `KubernetesJobExecutor` behind the PRD-013 executor interface,
external Temporal worker wiring, OpenTelemetry Collector deployment, health probes, least-privilege
service accounts, network policies, resource controls, optional GPU placement, and a complete
artifact-to-Kubernetes-Job acceptance smoke. It implements PRD-014 only; discovery CronJobs and
queue-driven autoscaling remain PRD-015/016.

## Architecture changes

- Adds `KubernetesJobExecutor` and a minimal in-cluster Kubernetes API client without changing the
  canonical domain-independent job contracts.
- Translates strict CPU, memory, GPU, command, argument, environment, network, timeout, trace, and
  attempt fields into bounded `batch/v1` Jobs.
- Keeps retry/cancellation/publication authority in the durable PostgreSQL job service while using
  Kubernetes for placement and Pod replacement.
- Adds API startup/liveness/readiness endpoints with strict Pydantic response contracts.
- Adds an external Temporal worker composition root and deterministic runtime-probe workflow.
- Adds credential-free Kustomize base resources for API, web, workflow workers, job scheduler,
  evaluation workers, CPU workers, OpenTelemetry Collector, service accounts, RBAC, PVC, and
  network policies.
- Adds kind lifecycle automation that keeps PostgreSQL and MinIO outside Kubernetes, securely
  creates a runtime Secret from the ignored local environment, builds/loads the application image,
  and waits for rollout.
- Adds a Kubernetes smoke Job that uploads the preserved historic fixture, executes normalization
  through the generic API and Kubernetes executor, and verifies its immutable 40-record output.

## Migration table

| Previous behavior | PRD-014 behavior | Reason |
|---|---|---|
| Finite jobs ran only through host Docker | The same strict specification may run through a Kubernetes Job | Deployed scheduling must preserve the tested executor contract. |
| Runtime services were defined only in Compose | Long-lived services and workers have Kustomize Deployments | Kubernetes is the target placement and replacement layer. |
| Generic retry state could have been duplicated by an orchestrator | Kubernetes Job retry is disabled and each failure becomes one durable attempt | Retry history must remain inspectable and idempotent. |
| Worker inputs/outputs used local bind mounts | Kubernetes attempts use isolated PVC subpaths and still publish immutable S3 artifacts | Pods need a shared bounded transport without making the PVC canonical storage. |
| API exposed a combined dependency health route | Startup, liveness, and readiness have separate contracts | Kubernetes must distinguish a live process from one ready to serve traffic. |
| No Kubernetes identity boundary existed | Separate service accounts and namespaced job-controller RBAC are explicit | Only scheduler workers need Kubernetes API authority. |
| Temporal was only an architectural boundary | A real externally connected worker image/entry point is deployable | Durable workflows need an independent runtime without running Temporal in-cluster. |
| No cluster-level trace receiver existed | An OpenTelemetry Collector accepts OTLP with bounded debug export | Workloads need a standard trace propagation destination. |

No database migration or public JSON Schema change is required. Generic job contracts from PRD-013
remain byte-for-byte compatible.

## Preserved behavior

- `LocalDockerExecutor` remains the default local executor and its security controls are unchanged.
- The Oduah baseline still normalizes to exactly 40 records.
- Compose remains supported for the complete local prototype and storage-only development.
- All immutable artifact, append-only review, pipeline, metrics, golden-dataset, extraction, and
  densitometry behavior remains unchanged.
- Existing job IDs, attempt history, cancellation, retry, logs, and output publication stay in
  PostgreSQL/S3 rather than moving into Kubernetes objects.

## Removed behavior

No retained application behavior is removed. Production Kubernetes configuration no longer permits
implicit in-cluster durable dependencies or committed Secret values. Kubernetes workers receive only
their explicit service-account permissions and configured environment.

## Setup and testing

```bash
uv sync --locked --all-extras
make check
kubectl kustomize infra/kubernetes/base >/tmp/hiveblot-base.yaml
kubectl kustomize infra/kubernetes/overlays/kind >/tmp/hiveblot-kind.yaml
docker build -t hiveblot:prd-014 .
make local-env
make kind-up
make kind-smoke
make kind-down
uv build
```

Focused verification covers Kubernetes API responses, manifest translation, GPU placement,
cancellation, timeout, log limits, strict health responses, service-account scope, Pod hardening,
resource bounds, network policy, secret rendering, Temporal registration, and durable result
publication.

  schema snapshots passed.
- The base and kind overlay rendered successfully with kubectl v1.36.3.
- `docker build -t hiveblot:prd-014 .` and source-distribution/wheel builds succeeded; the wheel

## Known limitations and deferred work

- The local kind overlay does not run Temporal; it scales the workflow worker to zero. Deployed
  environments must provide managed Temporal, and scientific workflow definitions remain future
  work.
- The attempt PVC is ephemeral execution transport. Multi-node deployments require a suitable RWX
  storage class; orphan workspace garbage collection is deferred.
- NetworkPolicy behavior depends on the selected CNI; kind's default networking is not treated as a
  production enforcement test.
- The web Deployment temporarily uses the retained monolith ASGI image/entry point.
- OpenTelemetry has a debug exporter only; production trace storage and automatic application
  instrumentation are deferred.
- Application and collector images use reviewed version tags in source; release automation should
  substitute immutable registry digests.
- The kind dependency overlay requires a modern Docker Compose release with `!reset` override
  support so it can remove inherited host-port publications.
- Concrete scheduled discovery CronJobs belong to PRD-015. Queue-based autoscaling/KEDA and
  distributed fetching belong to PRD-016.
- No production PostgreSQL, object store, queue, Temporal server, ingress, certificate manager, or
  secrets manager is installed inside this cluster.
